### silent-failure-hunter

> I reviewed the PR on `andrew/356-postprocesssvg-malformed-href` against `origin/main`, the full `build/postprocessSvg.mjs` file (notably the unwrap step that the diff does not show), and the upstream caller in `build/buildScores.mjs`. The PR converts a previously-throwing `decodeURIComponent(href)` call into a try/catch that sets `href = null` and then guards the two `href.includes(...)` checks with `if (href)`. Here is what my error-handling specialism turns up.
>
> **1. Severity: important — `build/postprocessSvg.mjs:198-200` — `catch (e) { href = null; }` is a textbook silent swallow.** The catch block names the error (`e`) and discards it. No `console.warn`, no `console.error`, no telemetry, no count returned to the caller. A LilyPond SVG that contains a malformed `xlink:href` is, by the ticket's own framing, a signal of upstream corruption — either a LilyPond bug, a filesystem path with an unexpected percent sequence, or a textedit URI mangled in transit. Right now, the build completes "successfully" and the user has no way of knowing that one or more anchors were skipped. Six months from now, when a chorister reports that clicking a note doesn't jump to the right line in the source, the developer has zero breadcrumb trail. At minimum this should emit `console.warn(...)` so the message lands in the buildScores stdout that already carries the surrounding `Post-processing ${svg}...` log line. The catch parameter `e` is currently unused, which most linters will flag and which itself is evidence that the author intended to swallow rather than report.
>
> **2. Severity: critical — `build/postprocessSvg.mjs:219-238` — the unwrap step runs unconditionally for null-href anchors, exactly as the ticket flags, but with no logging that this is happening.** Trace the control flow when `href` is `null`: line 202 sets `partIndex = null`, the `if (href)` guard at line 204 skips the includes-checks (correct), `partIndex` stays `null`, the `if (partIndex !== null)` guard at line 219 skips the data-part decoration (correct), and then execution falls through to lines 232-238 which unwrap the anchor unconditionally. This is consistent with the ticket's stated expectation ("Malformed anchors are unwrapped but receive no `data-part` attribute") — so the behaviour is intentional — but it is still a silent fallback: the resulting SVG looks indistinguishable from one whose anchors were perfectly well-formed but happened to point outside the variable ranges. There is no `data-malformed-href` marker, no console warning, no count. If a future regression starts producing thousands of malformed hrefs in every build (e.g. LilyPond upgrade changes URI encoding), nothing in the pipeline will notice. The fallback is justified by the ticket but undocumented in the code and unobservable at build time. Add a comment at line 199 explaining the intentional fallback, and lift a counter (e.g. `malformedHrefCount`) into a `console.warn` at the end of `postprocessSvg` if it is non-zero.
>
> **3. Severity: important — `build/postprocessSvg.mjs:198` — `catch (e)` is a maximally-broad catch.** `decodeURIComponent` is documented to throw exactly one thing: `URIError`. Anything else thrown from line 197 — `TypeError` from a non-string `href` due to a future refactor, an out-of-memory error, a thrown string from a custom `URIError` polyfill — will also be silently coerced to `href = null`. This is a small surface area today (one line, one well-typed call) but it is the wrong shape for a defensive catch. The narrower form is `catch (e) { if (e instanceof URIError) { href = null; } else { throw e; } }`, or equivalently a guard on the input shape before calling `decodeURIComponent`. As written, if `href` somehow becomes `undefined` between line 193 and line 197 (it can't today, but a future edit could break the invariant), the `TypeError: Cannot read properties of undefined` would be swallowed as if it were a URI problem, and the bug would be invisible.
>
> **4. Severity: suggestion — `build/postprocessSvg.mjs:196-200` — the catch lacks the contextual breadcrumbs that would make a Sentry-equivalent log useful.** Even if the team decides a `console.warn` is the right surface, the message will be useful only if it carries: the svgPath being processed, the offending href (raw, pre-decode), and the position in the document. Right now the catch has all of this in scope. If you add logging, include all three pieces or the log will not survive contact with a real bug report.
>
> **5. Severity: suggestion — `src/test/postprocessSvg.test.ts:54-87` — the new test asserts non-throw and non-presence of `<a>`, but does not assert the absence of `data-part` on the malformed anchor's child, nor does it assert that any warning was emitted.** The comment at lines 84-86 explicitly waves away the data-part assertion ("may or may not"). That is a missed opportunity: the ticket's stated expected behaviour is "Malformed anchors are unwrapped but receive no `data-part` attribute" — that is exactly what should be asserted. The malformed anchor in the test fixture contains `<text>malformed</text>`; the test should `expect(output).toMatch(/<text[^>]*>malformed<\/text>/)` and crucially `expect(output).not.toMatch(/<text[^>]*data-part[^>]*>malformed/)`. Without that assertion, a future regression that accidentally tags malformed anchors with a misleading `data-part="0"` will pass the test. Also: if you adopt finding #1's `console.warn`, the test should `vi.spyOn(console, "warn")` and assert the call.
>
> **6. Severity: suggestion — `build/postprocessSvg.mjs:33-56` — pre-existing:** `parseVariables` performs `readFileSync` and regex matching with zero defensive handling for `PART_INDICES[partName]` returning `undefined`. This is out-of-scope for the ticket but it's a pre-existing silent-failure pattern that your audit asked me to surface. If a LilyPond file ever contains a `notesIVA<Something>` variable where `Something` is not in `PART_INDICES`, line 52 pushes `[start, end, undefined]` into the partMap. `findPartIndex` will later return `undefined` (not `null`), the `partIndex !== null` check at line 219 will pass (because `undefined !== null` is true), and `setAttribute("data-part", String(undefined))` will write the literal string `"data-part=\"undefined\""` into the SVG. There is no log, no throw, no test. Worth a follow-up ticket.
>
> **7. Severity: suggestion — `build/buildScores.mjs:156-160` — pre-existing:** the inner `try { rmSync(...) } catch {}` is an empty catch with no parameter and no comment beyond "ignore cleanup failure". Again out-of-scope for #356, but flagging it because your prompt asked about adjacent silent failures.

> **8. Severity: suggestion — `build/postprocessSvg.mjs:184` — pre-existing:** `readFileSync(svgPath, "utf-8")` is unguarded. If the svg file is missing or unreadable, the throw bubbles up to `buildScores.mjs:155` where it is caught, logged with `console.error`, and `process.exit(1)` is called. This is actually fine — the caller handles it well — but it is worth noting that the function `postprocessSvg` itself makes no guarantees about which errors it can throw.
>

### type-design-analyzer

> Caveat up front: this is a `.mjs` file (plain JavaScript with JSDoc), not TypeScript. There is no static type checker enforcing anything — the JSDoc on `postprocessSvg` does not annotate `href` at all. So everything below is conceptual type design: what the *de facto* type of `href` is after the change, and whether the invariants implied by that type are honoured. The test file is `.ts` but does not exercise types of internals.
>
> Before the diff, `href` inside the loop had the implicit type `string` from line 197 onward. The post-condition of "we reach the includes() checks with a decoded string" was upheld by `decodeURIComponent` throwing — uncaught — and crashing the build. After the diff, the implicit type of `href` from line 200 onward is `string | null`, where `null` is the sentinel for "decode failed". The downstream code is guarded by `if (href)` at line 204.
>
> Ratings for the `string | null` post-condition:
>
> - Encapsulation: 4/10. The "decode failed" state is represented by mutating the same `let` binding from `string` to `null`. The failure mode is not a separate variable, not a wrapped result, not a named constant — it's an in-band sentinel that reuses the variable. Any future maintainer adding code between lines 200 and 204 will see a variable called `href` and reasonably assume it is a non-null string. The encapsulation of "this might be undecodable" lives entirely in the reader's memory of the try/catch four lines above.
>
> - Invariant expression: 3/10. The invariant being expressed is "downstream code only sees successfully-decoded URIs." This is communicated solely by the `if (href)` guard, which is indistinguishable from a generic truthiness check. There is no name, no type alias, no JSDoc, and no comment explaining that `null` specifically means "decodeURIComponent threw."
>
> - Invariant usefulness: 7/10. The invariant itself — "don't run regex/`includes` on an undecoded or partially-decoded URI" — is genuinely useful and aligned with the bug being fixed. Skipping the part-index assignment on malformed hrefs is the correct behaviour: the anchor still gets unwrapped so the SVG remains well-formed.
>
> - Invariant enforcement: 5/10. Enforcement is local and fragile. It works *today* because the only producer of `href = null` is the catch block, the only consumer is the `if (href)` at line 204, and nothing between them touches `href`. But there is no structural enforcement preventing a future edit from (a) adding a `.toLowerCase()` call before the guard, (b) widening the guarded block, or (c) re-using `href` later in the loop body.
>
> Finding 1 — Sentinel `null` is in-band and unnamed. Severity: **important**. `build/postprocessSvg.mjs:199`. Reassigning `href` to `null` inside the catch block uses `null` as an in-band sentinel meaning "decode failed." The same variable name carries two semantically different states (a decoded URI string vs. a decode-failure marker) with no syntactic distinction. A structured local like `const decoded = tryDecode(href); if (!decoded.ok) { ... }` or simply `continue`-ing inside the catch would eliminate the dual-state variable entirely. The cleanest fix in this file would be `continue` in the catch — except the unwrap must run regardless, so `continue` is unsafe here. That fact alone — that `continue` is unsafe because the unwrap must run regardless — is itself a design smell worth surfacing.
>
> Finding 2 — Loop body conflates two responsibilities, forcing the null sentinel. Severity: **important**. `build/postprocessSvg.mjs:191-239`. The loop does two unrelated things per anchor: (a) compute `partIndex` from the href, and (b) unwrap the anchor element. These are independent. Because they share a loop iteration, a `continue` on decode failure would skip the unwrap, which is why the author had to invent the `string | null` sentinel instead. Splitting into two passes (first pass: collect `{aElem, partIndex}` pairs, with decode failures yielding `partIndex = null` naturally; second pass: unwrap all anchors) would let the decode-failure case be expressed by simply not pushing into the first pass's result, with no sentinel needed.
>
> Finding 3 — No wrapped `decodeURIComponent` helper. Severity: **suggestion**. `build/postprocessSvg.mjs:196-200`. A one-line helper `function tryDecodeURIComponent(s) { try { return decodeURIComponent(s); } catch { return null; } }` (with a JSDoc `@returns {string | null}`) would (a) name the operation, (b) give the null state a documented home, (c) let the call site read `const decoded = tryDecodeURIComponent(href);` so the nullability is visible at the binding, and (d) be reusable if any other build script ever needs the same protection. The current inline try/catch buries the protection inside business logic.
>
> Finding 4 — `let href` declaration is now misleading. Severity: **suggestion**. `build/postprocessSvg.mjs:192`. `let href = aElem.getAttributeNS(...) || aElem.getAttribute("href");` initialises `href` as `string | null` (from the DOM API), is narrowed to `string` by line 194, then is widened back to `string | null` by the catch. A cleaner pattern would use distinct `const` bindings for distinct states.
>
> Finding 5 — JSDoc gives no contract for the null state. Severity: **suggestion**. `build/postprocessSvg.mjs:163-167`. The JSDoc on `postprocessSvg` documents only the three path parameters. There is no `@throws` clause and no documentation that malformed hrefs are silently skipped. Given the bug being fixed is precisely "crashes on malformed href," the new contract ("malformed hrefs produce an unwrapped anchor with no data-part attribute") deserves to be stated in the JSDoc.
>
> Finding 6 — Test asserts non-throwing but does not pin the post-condition. Severity: **suggestion**. `src/test/postprocessSvg.test.ts:78-87`. The test asserts `not.toThrow()` and that anchors are unwrapped, but the inline comment explicitly says "Malformed anchor should have no data-part; well-formed may or may not depending on whether the href matches a variable range." This leaves the invariant "malformed href produces no data-part attribute" untested. Given that *not* setting `data-part` on the malformed element is the entire behavioural meaning of the `if (href)` guard, that branch is currently uncovered by assertion.
>
> Finding 7 — Catch parameter `e` is unused. Severity: **suggestion**. `build/postprocessSvg.mjs:198`. Minor: `catch (e)` binds an unused error. Modern Node supports `catch {` (optional catch binding). Cosmetic, but the named binding also slightly invites a future maintainer to think there is something to do with `e` when in fact the decision is to silently swallow.
>
> Summary: there are no **critical** findings — the change does fix the crash, the downstream guard does cover the only path that would dereference the sentinel, and the unwrap behaviour on malformed anchors is correct. The findings are **important** on the structural choice (in-band null sentinel forced by an overloaded loop body) and **suggestions** on naming, scoping, documentation, and test coverage of the new invariant. The single biggest type-design improvement available without overengineering is **Finding 3** (a named `tryDecodeURIComponent` helper with JSDoc), which gives the nullable post-condition a name and a documented home without restructuring the loop. **Finding 2** (split the loop) is the more principled fix but is a larger change.
